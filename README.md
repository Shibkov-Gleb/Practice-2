# Практическая работа 2 — вариант 30, этап 1

Минимальный CLI-прототип инструмента визуализации зависимостей npm.
Реализован **только первый этап**: загрузка настроек из XML, проверка
каждого параметра и вывод всех шести значений в формате `ключ=значение`.

Приложение использует только стандартную библиотеку Python. Оно не получает
зависимости, не обращается к сети, не выполняет обход графа, фильтрацию или
построение изображения. Эти операции относятся к следующим этапам.
Файл тестового репозитория на этом этапе проверяется на наличие и возможность
чтения; его содержимое не разбирается.

## Требования и запуск

Python **3.9 или новее**. Установка дополнительных пакетов не нужна.
Команды выполняются из корня проекта, если не указано иное.

```sh
python3 -B -m src.main --config examples/config.xml
```

Скрипт запуска самостоятельно переходит в каталог проекта:

```sh
./run.sh --config examples/config.xml
./run.sh --config examples/test_config.xml
./run.sh --help
```

Если исполняемый бит не сохранился, используйте `sh run.sh` с теми же опциями.
Переменная окружения `PYTHON` позволяет выбрать интерпретатор для `run.sh`:

```sh
PYTHON=python3 sh run.sh --config examples/config.xml
```

Опция `--config FILE` обязательна и выбирает XML-файл. Путь `FILE` определяется
относительно текущего каталога запуска. Все шесть пользовательских настроек
берутся исключительно из XML; опции для их переопределения отсутствуют.
Опция `--help` выводит справку.

## Конфигурация

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config>
    <package>express</package>
    <repository>https://registry.npmjs.org</repository>
    <test_mode>false</test_mode>
    <output_file>graph.svg</output_file>
    <ascii_tree>true</ascii_tree>
    <filter_substring>debug</filter_substring>
</config>
```

| Параметр | Назначение и проверка |
| --- | --- |
| `package` | Имя пакета: `express`, `@scope/name` или `A` для тестов. |
| `repository` | HTTP(S)-адрес; при `test_mode=true` — читаемый локальный файл. |
| `test_mode` | Режим тестового репозитория; строго `true` или `false`. |
| `output_file` | Имя будущего изображения с расширением `.svg`. |
| `ascii_tree` | Настройка будущего вывода ASCII-дерева: `true` или `false`. |
| `filter_substring` | Подстрока для будущей фильтрации; пустая отключает фильтр. |

Все элементы обязательны, включая пустой `<filter_substring />`.
Порядок элементов XML произвольный. Регистр имён элементов и логических
значений учитывается. Внешние пробелы и переводы строк в значениях обрезаются.
Неизвестные и повторяющиеся элементы, вложенные теги, атрибуты и посторонний
текст отклоняются.

Правила проверки значений:

- Имя пакета начинается с латинской буквы или цифры, затем разрешены также
  `.`, `_`, `-`. Допускается префикс `@scope/` с теми же правилами для scope.
  Пробелы, версии, пустые компоненты и посторонние символы запрещены.
  Это проверка имени прототипом, а не полная проверка правил публикации npm.
- URL должен иметь схему `http` или `https`, сервер и корректный порт, если
  он указан. Пробелы, логин и пароль в URL запрещены. Доступность сервера
  по сети на первом этапе не проверяется.
- В тестовом режиме вместо URL требуется существующий читаемый обычный файл.
  Пробелы в имени локального файла разрешены.
- Для выходного файла требуется существующий каталог и доступ на запись.
  Путь не должен указывать на каталог. Расширение `.svg` проверяется без
  учёта регистра в соответствии с форматом изображения варианта 30.
  Файл не создаётся и не перезаписывается.
- Подстрока фильтра должна состоять из печатных символов одной строки.
  Внутренние переводы строк, табуляция и другие управляющие символы запрещены.

Относительные пути `repository` и `output_file` отсчитываются **от каталога
XML-файла**. Абсолютные пути также допустимы. `~` и переменные окружения
внутри XML не раскрываются. На экран выводятся исходные значения после
обрезки внешних пробелов, а не абсолютные пути.

## Примеры использования

Запуск с `examples/config.xml` выводит:

```text
package=express
repository=https://registry.npmjs.org
test_mode=false
output_file=graph.svg
ascii_tree=true
filter_substring=debug
```

Запуск с `examples/test_config.xml` выводит:

```text
package=A
repository=repository.json
test_mode=true
output_file=test_graph.svg
ascii_tree=false
filter_substring=
```

Успешное завершение возвращает код `0`. Ошибка конфигурации или аргументов
возвращает код `2`; сообщение идёт в `stderr`, обычный вывод остаётся пустым.
Для ошибок конфигурации трассировка исключения не выводится.
Если ошибок несколько, сообщается первая обнаруженная; после её исправления
приложение проверяет конфигурацию заново.

## Демонстрация ошибок

```sh
python3 -B -m tools.demo_errors
```

Команда создаёт временные XML-файлы, поочерёдно меняет каждый параметр,
запускает настоящий CLI и показывает сообщение и код завершения.
Временные файлы автоматически удаляются.

| Параметр | Ошибочное значение | Ожидаемый результат |
| --- | --- | --- |
| `package` | `bad name` | Ошибка имени пакета. |
| `repository` | `ftp://example.org` | Требуется HTTP(S)-адрес. |
| `test_mode` | `yes` | Допустимы только `true` и `false`. |
| `output_file` | `graph.png` | Требуется расширение `.svg`. |
| `ascii_tree` | `1` | Допустимы только `true` и `false`. |
| `filter_substring` | Две строки | Запрещены управляющие символы. |

Например, при `<ascii_tree>1</ascii_tree>`:

```text
Ошибка конфигурации: ascii_tree: допустимы только true или false.
```

Тесты также проверяют пропуск каждого параметра, пустые значения, повреждение
XML, неверную структуру документа, ошибки файлов и путей, порт URL, права
доступа и запуск из другого каталога.

## Сборка, тесты и проверка оформления

Отдельная сборка для запуска Python-приложения не требуется. При необходимости
можно скомпилировать исходники в байт-код; он исключён из Git:

```sh
python3 -m compileall -q -b src
python3 -B -m unittest discover -s tests -v
python3 -B -m tools.check_style
```

Автономная проверка контролирует длину строк до 79 символов, строки docstring
до 72 символов, отсутствие табуляции и концевых пробелов, наличие документации,
размер файла до 1000 строк, функции до 40 строк и до 7 аргументов.
Она также оценивает сложность по AST с учётом ветвлений, логических операций
и генераторов; предельное значение — 10. Эта проверка покрывает перечисленные
ограничения и не заменяет полноценный линтер PEP 8.

Имена, отступы, расположение импортов и оформление кода следуют PEP 8.
Константы используются вместо числовых литералов в сравнениях.
Документация функций оформлена docstring.

При установленном `make` доступны эквивалентные команды:

```sh
make run
make build
make test
make check
make demo-errors
```

Переменную `PYTHON` можно передать и в `make`, например `make test PYTHON=python3`.

## Структура и функции

```text
src/                   исходный код
tests/                 модульные и интеграционные тесты unittest
tools/                 автономная проверка и демонстрация ошибок
examples/              два XML-примера и тестовый репозиторий
run.sh                 скрипт запуска
Makefile               команды запуска и проверки
.gitignore             исключения для служебных и сгенерированных файлов
README.md              документация
```

### `src/config.py`

| Объект | Назначение |
| --- | --- |
| `Config` | Неизменяемая dataclass с шестью проверенными параметрами. |
| `FIELD_NAMES` | Имена параметров в порядке вывода. |
| `load_config(path)` | Чтение XML и преобразование ошибок в `ConfigError`. |
| `_read_fields(root)` | Проверка набора полей и получение строковых значений. |
| `_validate_root(root)` | Проверка корневого элемента `<config>`. |
| `_validate_element(element)` | Проверка структуры отдельного параметра. |
| `_build_config(values, base_path)` | Валидация значений и создание `Config`. |

### `src/validation.py`

| Объект | Назначение |
| --- | --- |
| `ConfigError` | Единое исключение для ошибок конфигурации. |
| `validate_package(value)` | Проверка имени пакета. |
| `parse_boolean(value, name)` | Преобразование `true`/`false` в `bool`. |
| `resolve_path(value, base_path)` | Разрешение относительных путей. |
| `validate_repository(value, test_mode, base_path)` | Выбор проверки URL или файла. |
| `_validate_url(value)` | Проверка синтаксиса URL без сетевого запроса. |
| `_validate_test_file(value, base_path)` | Проверка наличия и читаемости файла. |
| `validate_output(value, base_path)` | Проверка имени будущего SVG-файла. |
| `_validate_output_location(path)` | Проверка каталога и прав записи. |
| `validate_filter(value)` | Проверка допустимости подстроки. |

### `src/main.py`

| Функция | Назначение |
| --- | --- |
| `create_parser()` | Обработка `--config FILE` и `--help`. |
| `format_config(config)` | Формирование шести строк `ключ=значение`. |
| `main(argv=None)` | Запуск приложения и обработка `ConfigError`. |

### Вспомогательные команды

`tools/demo_errors.py`: `demonstrate_error(directory, name, value)` создаёт
один неверный XML и проверяет результат CLI; `main()` выполняет шесть примеров.

`tools/check_style.py`: `check_lines(lines)` проверяет строки;
`estimate_complexity(node)` оценивает сложность; `check_function(node)`
проверяет ограничения функций; `check_docstring(node, lines)` проверяет
документацию; `check_file(path)` объединяет проверки файла; `main()`
проверяет все Python-файлы в `src`, `tests` и `tools`.

В `tests/helpers.py` функция `write_config(directory, **changes)` создаёт
временные XML для тестов; `run_cli(*arguments)` в `tests/test_cli.py` запускает
CLI в отдельном процессе. Назначение каждого теста описано его docstring.
