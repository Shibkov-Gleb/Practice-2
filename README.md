
# Практическая работа 2 — вариант 30, этапы 1–4

CLI-инструмент анализа графа зависимостей npm. Реализованы загрузка и проверка
шести настроек XML (этап 1), получение прямых зависимостей из npm-реестра
(этап 2), построение транзитивного графа алгоритмом BFS без рекурсии,
фильтрация, обработка циклов и локальный тестовый режим (этап 3).

Используется только стандартная библиотека Python: `urllib.request` для HTTP,
`json` для разбора ответа. Менеджеры пакетов, сторонние библиотеки получения
зависимостей, Node.js и установленный npm не требуются.

Список параметров `ключ=значение` выводился только на первом этапе, список
прямых зависимостей — на втором. Теперь приложение выводит весь достижимый
граф списками смежности в порядке BFS. Обратные зависимости, ASCII-дерево
и создание изображения относятся к этапу 5. Режим обратных зависимостей
четвёртого этапа запускается отдельной точкой входа `src.reverse`.

## Требования и запуск

Python **3.9 или новее**. Установка дополнительных пакетов не нужна.
Команды выполняются из корня проекта, если не указано иное.

```sh
python3 -B -m src.main --config examples/config.xml
```

Скрипт запуска самостоятельно переходит в каталог проекта:

```sh
./run.sh --config examples/config.xml
./run.sh --config examples/test_config.xml
./run.sh --config examples/test_cycle.xml
./run.sh --config examples/test_filter.xml
./run.sh --config examples/scoped_config.xml
./run.sh --config examples/no_dependencies.xml
./run.sh --help
```

Если исполняемый бит не сохранился, используйте `sh run.sh` с теми же опциями.
Переменная окружения `PYTHON` позволяет выбрать интерпретатор для `run.sh`:

```sh
PYTHON=python3 sh run.sh --config examples/config.xml
```

Опция `--config FILE` обязательна и выбирает XML-файл. Путь `FILE` определяется
относительно текущего каталога запуска. Все шесть пользовательских настроек
берутся исключительно из XML; опции для их переопределения отсутствуют.
Опция `--help` выводит справку.

## Конфигурация

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config>
    <package>express</package>
    <repository>https://registry.npmjs.org</repository>
    <test_mode>false</test_mode>
    <output_file>graph.svg</output_file>
    <ascii_tree>true</ascii_tree>
    <filter_substring>debug</filter_substring>
</config>
```

| Параметр | Назначение и проверка |
| --- | --- |
| `package` | Имя пакета: `express`, `@scope/name` или `A` для тестов. |
| `repository` | HTTP(S)-адрес; при `test_mode=true` — читаемый локальный файл. |
| `test_mode` | `false` — HTTP-запросы npm, `true` — чтение локального JSON-графа. |
| `output_file` | Имя будущего изображения с расширением `.svg`. |
| `ascii_tree` | Настройка будущего вывода ASCII-дерева: `true` или `false`. |
| `filter_substring` | Исключает пакеты с этой подстрокой в имени; пустая отключает фильтр. |

Все элементы обязательны, включая пустой `<filter_substring />`.
Порядок элементов XML произвольный. Регистр имён элементов и логических
значений учитывается. Внешние пробелы и переводы строк в значениях обрезаются.
Неизвестные и повторяющиеся элементы, вложенные теги, атрибуты и посторонний
текст отклоняются.

Правила проверки значений:

- Имя пакета начинается с латинской буквы или цифры, затем разрешены также
  `.`, `_`, `-`. Допускается префикс `@scope/` с теми же правилами для scope.
  Пробелы, версии, пустые компоненты и посторонние символы запрещены.
  Это проверка имени прототипом, а не полная проверка правил публикации npm.
- URL должен иметь схему `http` или `https`, сервер и корректный порт, если
  он указан. Пробелы, логин и пароль в URL запрещены. Доступность сервера
  по сети проверяется при запросе метаданных. DNS-метки не должны быть пустыми,
  начинаться или заканчиваться дефисом; их длина ограничена 63 символами,
  полное имя без конечной точки — 253 символами. Поддерживаются IPv4 и IPv6.
- В тестовом режиме вместо URL требуется существующий читаемый обычный файл.
  Пробелы в имени локального файла разрешены.
- Для выходного файла требуется существующий каталог и доступ на запись.
  Путь не должен указывать на каталог. Расширение `.svg` проверяется без
  учёта регистра в соответствии с форматом изображения варианта 30.
  Запись пути к каталогу вроде `graph.svg/` недопустима.
  Файл не создаётся и не перезаписывается.
- Подстрока фильтра должна состоять из печатных символов одной строки.
  Внутренние переводы строк, табуляция и другие управляющие символы запрещены.

Относительные пути `repository` и `output_file` отсчитываются **от каталога
XML-файла**. Абсолютные пути также допустимы. `~` и переменные окружения
внутри XML не раскрываются.

## Получение данных npm

Вариант 30 не задаёт версию пакета, поэтому запрашивается версия с тегом
`latest`: `GET <repository>/<package>/latest`. Имя scoped-пакета кодируется
в URL, например `@types/node` становится `@types%2Fnode`. Путь внутри URL
пользовательского реестра сохраняется; конечный `/` необязателен.
Параметры запроса сохраняются, фрагмент `#...` в HTTP-запрос не передаётся.

Для каждого достижимого, не исключённого фильтром имени выполняется один
запрос с `Accept: application/json` и тайм-аутом 10 секунд на сетевые операции
(`REQUEST_TIMEOUT` в `src/npm.py`). Повторные зависимости не запрашиваются.
Архивы пакетов не скачиваются и не устанавливаются.

Из ответа читаются:

- `dependencies` — обычные прямые зависимости;
- `optionalDependencies` — необязательные прямые зависимости. При совпадении
  имени запись отсюда заменяет запись в `dependencies`, как предусмотрено npm.

`devDependencies` нужны для разработки самого пакета, а `peerDependencies`
описывают требования к его окружению; в данном проекте они не включаются
в список прямых runtime-зависимостей. Теперь прямые связи каждого полученного
пакета используются для продолжения BFS и получения транзитивного графа.

Граф строится на уровне имён объявленных зависимостей с метаданными `latest`
для каждого имени. Разрешение диапазонов версий, `npm:`-алиасов и Git-адресов
не реализуется; результат не является деревом конкретной установки npm.
Функция второго этапа `fetch_direct_dependencies` по-прежнему возвращает
исходные спецификации версий, а обход третьего этапа использует имена.

Источники описания формата:
[официальный HTTP API реестра](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md)
и [поля package.json](https://docs.npmjs.com/cli/configuring-npm/package-json/).

## Обход BFS и фильтрация

В `src/graph.py` используется очередь `collections.deque`: следующий пакет
извлекается через `popleft()`, новые пакеты добавляются в конец. Рекурсивных
вызовов нет. Зависимости сортируются по имени для воспроизводимого порядка.
Узел отмечается обнаруженным при добавлении в очередь, поэтому общий пакет
анализируется один раз, даже если на него ссылаются несколько узлов.

Рёбра к уже обнаруженным узлам сохраняются в графе. Благодаря этому циклы
и самоссылки представлены корректно, но не вызывают бесконечный обход.
В результат включается только компонента, достижимая из `package` по
направлению зависимостей; несвязанные пакеты не выводятся.

`filter_substring` сравнивается с именем как обычная подстрока с учётом
регистра. Например, `debug` исключит `debug` и `my-debug-helper`, но не `Debug`.
Исключённый пакет не добавляется в граф и не загружается из npm. Его потомки
не анализируются, если до них нет другого пути через оставшиеся узлы.
Пустая подстрока отключает фильтрацию. Если совпал исходный пакет, граф пуст
и CLI сообщает об исключении исходного пакета; это успешный результат.

Поля `ascii_tree` и `output_file` проверяются при загрузке настроек, но пока
не влияют на вывод. Списки смежности не являются режимом ASCII-дерева.

## Формат тестового репозитория

При `test_mode=true` параметр `repository` содержит путь к UTF-8 JSON-файлу:

```json
{
    "A": ["B", "C"],
    "B": ["D"],
    "C": ["D"],
    "D": []
}
```

Ключи — имена пакетов из заглавных латинских букв `A-Z`, например `A`, `B`
или `ROOT`. Значения — массивы имён прямых зависимостей. Каждая упомянутая
зависимость должна иметь собственный ключ; пакет без зависимостей описывается
пустым массивом. Циклы и самоссылки разрешены. Повторяющиеся рёбра при обходе
объединяются; повторяющиеся ключи JSON считаются ошибкой.

Весь JSON проверяется до начала обхода, в том числе несвязанные компоненты.
Отсутствие исходного пакета, неверное имя, ссылка на неописанный узел,
повреждённый JSON и ошибка чтения файла дают понятное сообщение.
Пустой объект `{}` разрешён как репозиторий, но не содержит исходного пакета.

Файл читается относительно каталога XML. В тестовом режиме сетевых запросов
нет; используется тот же алгоритм BFS и тот же фильтр, что и для npm.

## Демонстрация и примеры использования

Все локальные примеры можно выполнить одной командой:

```sh
make demo-graphs
```

Она запускает CLI для шести случаев:

| Конфигурация в `examples/` | Случай |
| --- | --- |
| `test_config.xml` | Обычный граф `A -> B, C`. |
| `test_diamond.xml` | Общая транзитивная зависимость `D`. |
| `test_cycle.xml` | Цикл `A -> B -> C -> A` и самоссылка `D -> D`. |
| `test_filter.xml` | Исключение `B`; узел `D` остаётся достижимым через `C`. |
| `test_empty.xml` | Исходный пакет без зависимостей, несвязанные узлы пропускаются. |
| `test_filtered_root.xml` | Исключение исходного пакета. |

Пример с общей транзитивной зависимостью:

```sh
./run.sh --config examples/test_diamond.xml
```

```text
Граф зависимостей пакета A (BFS):
A -> B, C
B -> D
C -> D
D -> (нет зависимостей)
```

С `examples/test_cycle.xml` обход завершается и сохраняет оба вида циклов:

```text
Граф зависимостей пакета A (BFS):
A -> B, D
B -> C
D -> D
C -> A
```

С `examples/test_filter.xml`, где `filter_substring=B`:

```text
Граф зависимостей пакета A (BFS):
A -> C
C -> D
D -> (нет зависимостей)
```

С `examples/test_filtered_root.xml`, где `filter_substring=A`:

```text
Пакет A исключён фильтром.
```

Для npm `examples/config.xml` строит транзитивный граф `express`, исключая
имена с `debug`. Реальный результат зависит от текущих версий в реестре.

Запуск с `examples/no_dependencies.xml` для пакета без зависимостей:

```text
Граф зависимостей пакета is-number (BFS):
is-number -> (нет зависимостей)
```

`examples/scoped_config.xml` демонстрирует граф scoped-пакета `@types/node`.

Успешное завершение возвращает код `0`. Ошибка конфигурации или аргументов
возвращает код `2`, ошибка анализа графа или получения данных — код `1`.
Сообщения ошибок идут
в `stderr`, обычный вывод остаётся пустым. Трассировка исключения не выводится.
Если ошибок несколько, сообщается первая обнаруженная; после её исправления
приложение проверяет конфигурацию заново. При ошибке транзитивного узла
частичный граф не выводится: результат печатается только после полного BFS.

Для сетевого запроса обрабатываются HTTP 404 (пакет или `latest` не найден),
другие HTTP-ошибки, ошибки DNS, отказ соединения, тайм-аут и обрыв ответа.
Некорректный JSON, несовпадающее имя пакета, отсутствие версии и повреждённые
поля зависимостей также приводят к понятному сообщению.

## Демонстрация ошибок

```sh
python3 -B -m tools.demo_errors
```

Команда создаёт временные XML-файлы, поочерёдно меняет каждый параметр,
запускает настоящий CLI и показывает сообщение и код завершения.
Временные файлы автоматически удаляются.

| Параметр | Ошибочное значение | Ожидаемый результат |
| --- | --- | --- |
| `package` | `bad name` | Ошибка имени пакета. |
| `repository` | `ftp://example.org` | Требуется HTTP(S)-адрес. |
| `test_mode` | `yes` | Допустимы только `true` и `false`. |
| `output_file` | `graph.png` | Требуется расширение `.svg`. |
| `ascii_tree` | `1` | Допустимы только `true` и `false`. |
| `filter_substring` | Две строки | Запрещены управляющие символы. |

Например, при `<ascii_tree>1</ascii_tree>`:

```text
Ошибка конфигурации: ascii_tree: допустимы только true или false.
```

Тесты также проверяют пропуск каждого параметра, пустые значения, повреждение
XML, неверную структуру документа, ошибки файлов и путей, порт URL, права
доступа и запуск из другого каталога. HTTP-клиент проверяется на ответах npm,
сортировке, необязательных зависимостях, кодах HTTP и сбоях транспорта.
Автоматические тесты подменяют HTTP-ответы и не требуют доступа к сети;
настоящий запрос проверяется обычным запуском приложения. Дополнительно
проверяются порядок BFS, общие зависимости, циклы, самоссылки, фильтрация,
недостижимые узлы, структура тестового JSON и цепочка из 1500 узлов.

## Сборка, тесты и проверка оформления

Отдельная сборка для запуска Python-приложения не требуется. При необходимости
можно скомпилировать исходники в байт-код; он исключён из Git:

```sh
python3 -m compileall -q -b src
python3 -B -m unittest discover -s tests -v
python3 -B -m tools.check_style
```

Автономная проверка контролирует длину строк до 79 символов, строки docstring
до 72 символов, отсутствие табуляции и концевых пробелов, наличие документации,
размер файла до 1000 строк, функции до 40 строк и до 7 аргументов.
Она также оценивает сложность по AST с учётом ветвлений, логических операций
и генераторов; предельное значение — 10. Эта проверка покрывает перечисленные
ограничения и не заменяет полноценный линтер PEP 8. Также проверяются
строки комментариев до 72 символов и отсутствие числовых литералов
в сравнениях по правилу М1.

Имена, отступы, расположение импортов и оформление кода следуют PEP 8.
Константы используются вместо числовых литералов в сравнениях.
Документация функций оформлена docstring.

Для полноценной проверки PEP 8, имён, неиспользуемых импортов и сложности
можно установить отдельные инструменты разработки:

```sh
python3 -m pip install -r requirements-dev.txt
python3 -B -m flake8 src tests tools
```

Настройки находятся в `.flake8`: строки до 79 символов и сложность до 10.
Исключено устаревшее правило W503: перенос перед логическим оператором
соответствует действующим рекомендациям PEP 8. Зависимости разработки
не нужны для запуска приложения, тестов и автономной проверки.
В `.flake8` явно задано `ignore = W503`: другие стандартные исключения
Flake8 не скрывают проверки. Публичный интерфейс модулей `src` объявлен
через `__all__`, вспомогательные внутренние функции имеют префикс `_`.

Полная сверка с общими требованиями PDF, границы проверки и оставшиеся
организационные замечания перечислены в [AUDIT.md](AUDIT.md).

При установленном `make` доступны эквивалентные команды:

```sh
make run
make build
make test
make check
make lint
make demo-errors
make demo-graphs
```

Переменную `PYTHON` можно передать и в `make`, например `make test PYTHON=python3`.

## История разработки

Основная локальная история содержит три коммита с подробными сообщениями:

1. `feat(stage-1): implement validated XML configuration CLI` — XML,

## Этап 4: обратные зависимости

Все шесть настроек берутся из того же XML. Операция выбирается точкой входа:

```sh
python3 -B -m src.reverse --config examples/reverse_diamond.xml
make reverse
make demo-reverse
```

Для тестового режима анализируется **весь репозиторий**, включая вершины,
недостижимые при прямом обходе выбранного пакета. Рёбра разворачиваются,
после чего вызывается исходный BFS этапа 3. Вывод включает прямые и
транзитивные обратные зависимости, каждый пакет один раз, без исходного
пакета при цикле. Фильтр применяется перед посещением обратных соседей;
через исключённые вершины обход не продолжается. Другой путь остаётся доступен.

Примеры `reverse_diamond.xml`, `reverse_cycle.xml`, `reverse_empty.xml`,
`reverse_filter.xml` демонстрируют общую зависимость, цикл, отсутствие зависимых
пакетов и фильтр. Для D в ромбе выводятся B, C, A; с фильтром B — C, A.

В режиме npm область операции — загруженный прямой транзитивный граф.
Это **не глобальный поиск зависимых пакетов по всему npm**: получение метаданных
одного пакета не сообщает, кто на него ссылается. Область явно напечатана в CLI.
Для полного обратного поиска по заданному набору пакетов нужен локальный JSON,
содержащий весь этот набор. Неполный набор не выдаётся за полный публичный реестр.

Каждый этап представлен отдельной локальной веткой `codex/stage-1`…`codex/stage-4`.
Ветки содержат последовательные снимки проекта с тестами соответствующего этапа:

```sh
git switch codex/stage-1
make test check
git switch codex/stage-4
make test check demo-reverse
```

Публикация веток не выполняется: пользователь разрешил только локальные коммиты.
